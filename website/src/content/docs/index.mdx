Goliash watches what actually runs and tells you when a new release ships or when environments drift apart:
staging on 1.5.0 while prod is still on 1.3.2, or two prod clusters disagreeing.

## Meet Goli

**Goli** is the assistant inside Goliash, the gentle giant with the release bell. Ask it in plain words and it
looks things up for you, live, as you:

<div class="goli-chat">
<p class="goli-q">What should we upgrade first, and why?</p>
<p class="goli-a"><strong>payments-api in prod</strong>: it runs log4j-core 2.14.1, exploited in the wild; 2.16.0 fixes it.
Then <strong>postgres 15</strong>, end of life in a month…</p>
</div>

- **Answers from live data**, with links to the pages that show the details: what runs where, drift, updates,
  vulnerabilities, what changed, any moment in the past.
- **Briefs you on an upgrade**: it reads the release notes between what runs and the target and tells you what
  breaks, what it fixes and what to check.
- **Only reads, as you**: it sees what you may see and cannot change anything.
- **Opt-in and yours**: off until you give your server a model: Claude (the default), OpenAI, or one on your own
  hardware with Ollama or vLLM, so nothing leaves your network.

### What will this upgrade break?

Every upgrade on the Updates page has a **Brief** button. Goli reads the release notes of **every release between what
runs and the target**, straight from the project's GitHub or GitLab releases, and turns them into a checklist:
breaking changes and migrations first, then what it fixes (security first), then what to check before and after.
Keycloak 24 → 26 is three major versions of release notes; Goli reads them in half a minute and starts with what will
stop your login page from working.

It never calls an upgrade safe, and it says so when the notes are silent: the decision stays yours. Try it on the
[live demo](https://demo.goliash.dev/updates).

### An SBOM of what actually runs

Build-time SBOMs say what an image contains. Goliash says **which of those images run, where, and since when**: one
CycloneDX 1.6 document with every running image, its digest, the environment, cluster and service it runs in, and the
packages of its SBOM nested inside. Export it from the matrix or the Security page, for one environment or a moment in
the past, or let Dependency-Track track one project per environment:

```sh
curl -H "Authorization: Bearer $GOLIASH_TOKEN" \
  "https://goliash.example.com/api/v1/inventory?format=cyclonedx&environment=prod" \
  | curl -X POST "$DTRACK/api/v1/bom" -H "X-Api-Key: $DTRACK_API_KEY" \
      -F autoCreate=true -F projectName="goliash prod" -F projectVersion=running -F bom=@-
```

The software inventory the Cyber Resilience Act, NIS2 and your customers' questionnaires ask for, kept current by the
runtime itself. [How it works →](/guide/sbom/)

## How it works

```
 your network                                    Goliash server
┌─────────────────────────────────┐             ┌──────────────────────────────────┐
│ Kubernetes / ECS / Nomad /      │             │ ingest → mapping → versions      │
│ Swarm / Docker ─read-only─► agent ─HTTPS────► │   │                  │           │
│ private registries ──► agent    │  snapshots  │   ▼                  ▼           │
└─────────────────────────────────┘             │ events, matrix   notifier ──► Slack, webhook, e-mail
                                                │ UI, REST API     SQLite / Postgres│
                                                └──────────────────────────────────┘
```

The **agent** runs next to what it watches and sends full snapshots, so an outage loses nothing. The **server**
turns snapshots into history, maps containers to services, compares them with upstream releases and notifies
you. It can also collect what it reaches itself, without an agent.
